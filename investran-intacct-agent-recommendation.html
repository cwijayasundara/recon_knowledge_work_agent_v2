Architecture recommendation · private equity fund onboarding · 25 Sep 2026

An onboarding analyst agent for Investran → Sage Intacct

A knowledge-work agent that accepts whatever Investran extract a customer sends, works with the analyst the way a deep-research agent works with a user, writes and verifies the transformation as code, keeps the accounting rules deterministic, and improves every period. Runs on Azure Container Apps without LangSmith.

Prepared for: CK, VP EngineeringRevision 5 · consolidatedGrounded in the seven MVP1 process-flow documents, the mapping sheets, the sample data and the existing codebase
Summary

Treat onboarding as knowledge work, done by a coding agent that talks to the analyst, inside a workflow it cannot bypass

Knowledge-work automation, modelled on LangChain's paid-media agent, is the right way to frame this problem. Each customer's export is different, the rules are domain-specific, many steps need judgement, and the output is a structured deliverable that a person signs off. The competitor's Excel add-in confirms the direction. It is a small coding agent: a context box plus a step prompt produce one spill formula per step, and the formula in the cell is the audit trail.

The design adds four things the add-in and the current build both lack:

A conversationdeep-research style

A supervisor agent studies the files, asks a few precise questions with evidence, writes an onboarding brief for the analyst to approve, runs the work and reports back. Every user instruction is restated, dry-run and checked against the rules before it takes effect.

A program, not cell valuescoding-agent core

A coding subagent writes the transformation as Python against our own onboarding_sdk, runs the checks on its own output, and hands over a recipe that is approved, versioned and replayed without the model next period.

Rules it can't changedeterministic spine

A LangGraph workflow enforces the documented phases, analyst gates, locks and entity order. Accounting functions and validators live only in the SDK. The renderer refuses to write while a blocking finding is open.

Governed self-improvementlearning loop

Run notes, the store of approved decisions, and consolidation and trace-mining agents turn experience into proposed improvements. Each one passes an evaluation gate and a human approval.

Decision

Harness: Deep Agents (MIT, v0.7.x) on self-hosted open-source LangGraph with a Postgres checkpointer. Before committing, run a bake-off against the Claude Agent SDK for the coding subagent. Model: Claude via Microsoft Foundry, hosted on Azure. Code execution: Azure Container Apps dynamic sessions, custom container pool, Hyper-V isolated, no outbound network. State: PostgreSQL (with pgvector) and immutable Blob storage. Observability: OpenTelemetry into Application Insights.

01 · The problem

What the business does today, and which parts are knowledge work

A fund administrator moves each new sponsor's books from Investran into Sage Intacct. Seven flows run in a fixed order. Every file inside them passes through the same four or five phases, with an analyst gate at each boundary. The process is well documented. What varies is every customer's raw export: sheets, column names, sign conventions and naming.

GL is blocked until all static data is complete for the sponsor. In Dual-Level, the Entity run must be signed off before the LP file is uploaded.

02 · Where things stand

Why the current build feels primitive, and what the add-in gets right

The current solution is sound engineering: a policy engine, header binding, a dependency DAG and a COA cascade. Its weakness is where it allows flexibility. Only column headers may vary, so everything upstream has to be cleaned into an agreed template that the business never standardised. GenAI appears in two places, and everything else is forms. Users experience it as a form-filling tool, even though the Python behind it is good.

04 · Evidence

What is known about automating knowledge work with coding agents

UsageAnthropic, 2026

44% of Claude Code sessions are non-coding or code-adjacent. Writing and data analysis roughly doubled, from about 10% to 20%, between October 2025 and April 2026. Domain expertise predicted success more than coding background. Analysts, not developers, will drive the agent.

Code as actionCodeAct, ICML 2024

Agents acting through executable Python reached up to 20% higher success than JSON tool calls across 17 models, and revised their own actions after errors. Give the agent a Python SDK, not forty tools.

Code execution with MCPAnthropic

Tools exposed as code APIs cut one workflow from 150,000 to 2,000 tokens (98.7%). Intermediate data stayed in the execution environment, and working code could be saved as skills. GL rows stay in the sandbox; the model sees profiles and results.

Agent loopClaude Agent SDK

General agents gather context, take action and verify their work, and finance is a named use case. Agents that check their own output are more reliable. The coding subagent verifies before a human sees anything.

Data preparationsurvey, 2025

Having the model write code that transforms the data is more deterministic and scalable than having it produce the data directly. Hybrids that filter cheaply before calling the model do best. This continues the FlashFill → Auto-Tables → DataMorpher line of program synthesis. The recipe pattern.

Spreadsheet agentsSpreadsheetBench 2, WorkstreamBench

The best model passed 34.9% of end-to-end business spreadsheet workflows. Cell-level scores of 77–92% collapsed when every cell had to be right. Common failures included hardcoded values instead of formulas and off-by-one ranges. Cell-filling without a verification loop is fragile.

Clarify firstOpen Deep Research

Scoping starts by asking for missing context, because "users rarely provide sufficient context". The conversation is then compressed into a brief that steers the supervisor and subagents. The onboarding brief.

Skill librariesVoyager; LangChain

Agents that save verified programs as skills keep improving. LangChain's agent appends learnings every run and consolidates them into skills weekly. Recipes and resolutions become reusable knowledge.

What is new here: most published uses of coding agents are analysis or one-off tasks. Using one to write governed, replayable transformation programs for a regulated accounting process, with a conversation in front and deterministic gates behind, is uncommon. That combination is the story to tell the business.

05 · Solution overview

Five layers, from the conversation down to the ledger

The knowledge layer follows LangChain's split. Skills describe how to do the work and would apply at any fund administrator. Sponsor knowledge is true for one sponsor. Live reference data is the current Intacct COA, customers and vendors. Deterministic code covers everything that must be reproducible. The system prompt stays short and points to an index.md. Everything else is loaded when the phase needs it.

06 · Interaction model

A supervisor that works with the analyst the way a deep-research agent works with a user

The onboarding brief

The brief plays the role of the add-in's context box, except the agent writes it from evidence and the analyst approves it.

Sponsor: Sponsor-A · Fund IV · Entity 5001234 · Entity GL · Dual-Level · period 2026-06
Source:  GL_Detail sheet, header row 4, 1,284,330 rows; 'Total' rows dropped (318)
Columns: 19 mapped · 3 into DESCRIPTION (Comments | Batch memo) · 4 ignored (listed)
Amounts: DEBIT = Amount Local × −1   evidence: 412/412 batches net to zero; × +1 → 0/412
FX:      EXCHANGE_RATE = −Amount Legal Entity ÷ DEBIT; 37 rows default to 1 (WARN)
Journal: HJE; 6 batches with Adjustment Date → ADJ (confirm)
COA:     214 distinct keys · 188 golden · 17 TT-exact · 9 need your decision
Open questions: none blocking · 2 warnings to acknowledge

Keep the user's prompt short

  • The system assembles context from skills, sponsor knowledge, the recipe and the file profile
  • The agent drafts; the user types only corrections
  • Low-confidence items become one-click questions with evidence
  • Known decisions are buttons and dropdowns bound to typed fields
  • Approved instructions become rules, so next period needs none
  • Frequent requests are saved as named actions with parameters

Catch a wrong instruction

  • Restate it as a concrete change and confirm that version
  • Dry-run it: "with × +1, 0 of 412 batches balance"
  • Show rows changed, totals, new findings
  • Refuse anything that breaks a business rule, naming the rule
  • Ask when a name matches more than one column or sheet
  • Require a second approver for sponsor-wide changes; every change can be rolled back

The model's own context stays small too. Skills load on demand, the model sees profiles rather than rows, resolution runs over distinct keys, tools are discovered by search, and the stable prefix is prompt-cached. A useful product metric is typed words per onboarding. It should fall every period.

07 · Coding-agent core

The agent writes programs against our SDK, then compiles once and replays

The existing Python becomes a package in the sandbox image. The coding subagent imports it, composes it, and uses plain pandas or DuckDB only for layout quirks the SDK doesn't cover.

from onboarding_sdk import read, standardise, bind, resolve, gl, checks

wb   = read.workbook("in/gl_extract.xlsx", sheet="GL_Detail", header_row=4)
df   = standardise.gl(wb, drop=lambda r: r["Account"].isna())         # layout-specific cleanup
cols = bind.columns(df, entity="entity_gl")                            # string_matcher
df   = gl.amounts(df, debit="-Amount Local", base="-Amount Legal Entity")
df   = gl.reference_no(df, entity_id="5001234", journal="HJE")
coa  = resolve.coa(df.keys("Account Type", "GL Account", "Trans Type"))   # L0–L4 cascade
out  = gl.assemble(df, coa, variant="dual_level")
report = checks.run(out, ruleset="gl_journal")                         # ERR/WARN, zero-sum
assert report.blocking == 0, report.summary()

Recipe lifecycle

  1. Fingerprint the workbook structure: sheets, header row, columns, types, value patterns.
  2. Recall. If a recipe exists for this sponsor and fingerprint, replay it deterministically and review only what is new.
  3. Author. Otherwise the agent writes the brief and the recipe, then runs and self-verifies it.
  4. Approve. The analyst reads the brief, not the code, and edits in plain language.
  5. Freeze. Store the brief, code hash, check report, snapshots and approver. Replay produces the same bytes.
recipe: sponsor-a / entity_gl / fp:9c1e…
code_sha256: 4b7f…    policy: gl_journal@1.3.0    snapshots: coa@2026-09-01, inv_static@r17
approved_by: a.analyst  2026-09-24T10:12Z   checks: 0 ERR, 2 WARN acknowledged   rows: 1,284,330 → 1,284,330

This is the sponsor configuration the flow documents ask for ("column choices saved — auto-recalled for next period under this sponsor"), made complete and executable. GL rows never leave the sandbox. The renderer refuses to write while blocking findings exist, and line numbering and offsets exist only as SDK functions.

Following LangChain's agent profiles pattern, one runtime serves every entry point with different tools and skills: analyst workspace, monitor (file arrival, schedule, period close), SME/policy (skill and rule changes with merge rights), improvement (weekly job), and auditor (read-only manifests and lineage). Use a frontier model for the supervisor and a cheaper one for bulk sub-tasks. Static entities with no mutual dependency run in parallel. Only named approvers can approve a recipe, write to the golden COA store or publish.

10 · COA mapping

Where the agent earns its keep, and the problem the add-in could not solve

  1. Collapse the file to distinct Account Type | GL Account | Trans Type keys. A million-row GL typically has hundreds of them.
  2. Run L0–L4 deterministically: golden history (0.97), transaction-type exact (0.85), hybrid BM25 + vector with FS-grouping pre-filter (≥0.50), account-primary with reverse constraint.
  3. Give the resolver only what is left, with top candidates, the valid-account set, Bank Account narrowing, similar prior decisions and the sponsor's naming. It proposes an account with reasoning.
  4. The analyst confirms in bulk. Results go to the golden store and the client-specific store, so the next sponsor starts with better history.
11 · Review surface

Meet the analyst in Excel, with live formulas where they help

Alongside the Intacct CSV, the coding subagent generates a review workbook. This matches the add-in's in-cell audit trail.

  • Source: the rows as received.
  • Upload preview: derived columns written as real formulas that reference the source sheet, such as =IF(Commitment>0,Commitment,"") for INCREASE, or the REFERENCE_NO concatenation.
  • Resolutions: each COA, investor and DEPT_ID decision with route, score and reason.
  • Findings: rule code, affected rows, resolution.
  • Brief and recipe version: what was approved, by whom and when.

Very large GL extracts get a sample with lineage columns instead of live formulas. The renderer's CSV is the file of record.

12 · Self-improvement

The agent gets better every period, without changing the rules on its own

In the live session, LangChain described two loops. The agent appends learnings to agents.md on every run, and a weekly job turns them into skill and wiki edits. An "agent for agent engineering" reads recent traces and opens pull requests with improvements. Both carry over, with every change proposed, tested and approved.

ChannelLearnsApplied asApproved by
Run notesSponsor quirks seen during a runHints read at the next run for that sponsorNobody; hints never become rules
Decision flywheelApproved resolutions and column bindingsGolden and client stores, matcher alias historyAnalyst at the gate
ConsolidationRepeated corrections and questionsDiffs to sponsor knowledge, recipes, skillsSponsor lead or SME
Improvement agentLoops, bad tool calls, slow steps, warnings analysts always overridePRs to skills and SDK, threshold changesEngineering, after CI
Usage gapsQuestions the agent can't answer wellBacklog for SDK functions, reference data, connectorsProduct owner
  • The rules are out of reach. Validators, reconciliation, Intacct column contracts and policy change only through SMEs.
  • Every change is eval-gated. CI runs the expected.json fixtures and replays signed-off runs. Any change to past output must be declared, with the rows affected and the reason.
  • Locked runs never change. A correction to a signed-off period is a new run.
  • Sharing across sponsors is a policy choice. Skills and the golden store learn across sponsors. Sponsor knowledge stays with the sponsor unless the business decides otherwise.

What to settle early
